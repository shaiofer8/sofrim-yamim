- source_spec: `_bmad-output/implementation-artifacts/spec-2-3-settings-dialog.md`
  summary: The Settings dialog's notification toggle only re-checks `Notification.permission` when the dialog is opened (and after the user interacts with the toggle itself) — if the user changes the permission via the browser's own site-settings UI (e.g. the address-bar padlock) while the Settings dialog happens to still be open, the toggle/hint go stale until the dialog is closed and reopened.
  evidence: Blind-hunter review of Story 2.3 flagged this. Not fixed here because a live fix requires the `Permissions` API's `PermissionStatus.onchange` event (`navigator.permissions.query({name: "notifications"})`), a meaningfully bigger addition for an edge case (user has both the app's Settings dialog AND the browser's own permission UI open at the same time) that the story's AC doesn't ask for.

- source_spec: `_bmad-output/implementation-artifacts/spec-2-5-fallback-reminder-check.md`

  evidence: Blind-hunter review of Story 2.5 flagged this. - source_spec: `_bmad-output/implementation-artifacts/spec-3-1-ad-banner.md`
  summary: `#ad-banner` uses a generic responsive AdSense `<ins data-ad-format="auto" data-full-width-responsive="true">` unit inside a fixed bottom bar. A real responsive ad isn't guaranteed to fit any particular height, so `.event-list`'s matching `padding-bottom` is a best-effort estimate, not a guarantee the banner never covers the last row. Google's "Anchor ad" format exists specifically for this fixed-bottom-bar placement and handles sizing itself.
  evidence: Blind-hunter review of Story 3.1 flagged this. Not fixed here because switching to an Anchor ad requires actually configuring one in the AdSense dashboard (a real account, which doesn't exist yet) — not something achievable via HTML/CSS alone with a placeholder client id. Revisit once the real AdSense account exists, before shipping this to real users.
  **Partially resolved (2026-08-19):** this prediction underestimated the actual severity — with the placeholder client id, `adsbygoogle.js` didn't just fail to fill the slot, it forced an inline `!important` height on `#ad-banner` itself while trying (~390px, most of the screen, live-reproduced and screenshotted on a real device by the user during informal demoing). No CSS could override an inline `!important` set by someone else's script. Fixed by skipping the `push({})` call entirely when the placeholder client id is detected (`billing.js`'s `isPlaceholderAdClient`) — the SDK never touches the slot's sizing if it's never asked to fill it, so the banner stays fully hidden until a real AdSense account exists. The original 48px/Anchor-ad question above is now moot until then; revisit both together once real credentials exist.
