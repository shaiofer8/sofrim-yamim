- (question) MAJOR OPEN QUESTION surfaced via web research (github.com/GoogleChrome/android-browser-helper issue #535, as of mid-2025, still open): there is NO official/supported way to show AdMob native banner ads inside a pure Bubblewrap TWA - Chrome controls full-screen rendering, no native AdView overlay possible. Injecting AdSense/web ads into the PWA's own content is technically straightforward but explicitly flagged by that same thread as possibly violating AdMob/AdSense TOS for WebView/wrapped contexts (unclear enforcement in practice - many published Bubblewrap apps do run web ads anyway). This directly affects PRD FR-8 which assumed AdMob without knowing this constraint. Needs user decision before FR-8 architecture is finalized - see options surfaced to user.
- (decision) User (Shaio) chose: web ad tags (Google AdSense) rendered inline in the PWA's own HTML/JS, accepting the ambiguous TOS risk noted in GoogleChrome/android-browser-helper#535. This is a business/product-risk decision, not purely technical - flagged as such in spine Deferred section with the caveat and its source.
- (constraint) Verified via web search: Notification Triggers API (showTrigger, exact-time scheduled local notifications) is DISCONTINUED by Chrome ('no longer pursued' per Chrome capabilities project) - cannot be relied on. Periodic Background Sync API is the realistic alternative: Chromium/Android-only (fine, app is Android-only), requires installed PWA (already true for TWA), BUT gated by a per-site engagement score - low-engagement users may be denied periodic sync entirely, undermining reliability exactly for users who'd most need a reminder nudge.
- (decision) Notification architecture: Periodic Background Sync (best-effort, checks upcoming events, fires via ServiceWorkerRegistration.showNotification) as primary mechanism + check-on-app-open as fallback/backstop. No backend/push-server in v1 (stays consistent with PRD's client-only non-goal). Known limitation flagged: this cannot guarantee the PRD's 95%+ delivery NFR target purely client-side - true reliability would need a minimal server-side push scheduler, deferred to v2 if metrics show underperformance.
