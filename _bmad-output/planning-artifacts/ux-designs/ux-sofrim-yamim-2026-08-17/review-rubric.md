# Spine Pair Review — sofrim-yamim

## Overall verdict
The spine pair is well-grounded in the PRD and research (source citations resolve, section order matches the canonical shape exactly, and the ad-cleanliness/no-subscription thesis is honored throughout) but is **not yet clean for downstream extraction**. Four high-severity gaps would trip up an architect or story-dev reading only these two files: the Ad Banner — the component central to the app's whole differentiation thesis — has no spec row anywhere; the Settings surface is described as both a full screen and a bottom-sheet dialog in different sections; the notification-permission trigger described in EXPERIENCE.md contradicts PRD FR-6; and text/icons placed directly on the brand gradient (confirmed in the mockup) have no stated contrast target. These need fixing before the spine is handed off.

## 1. Flow coverage — adequate
Checked all three Key Flows against PRD UJ-1/UJ-2/UJ-3: each has a named protagonist matching the PRD persona (מיכל, דוד, נועה), numbered steps, and a labeled **שיא** (climax) beat. Flows 1 and 3 also carry an explicit **כשל:** (failure) line; Flow 2 does not.
### Findings
- **low** Flow 2 (UJ-2, EXPERIENCE.md lines 107–114) has no explicit `כשל:` line like Flows 1 and 3 — the substance (v1 doesn't auto-calculate Hebrew dates for personal events) is folded into step 5's prose instead of formatted as a distinct failure path. *Fix:* add a `כשל:` line for formatting consistency, or fold the FR-5 holiday-missing-date behavior (see §4 below) in as the real failure path for this flow.

## 2. Token completeness — thin
Every frontmatter color has a hex or rgba value; typography/rounded/spacing tokens are all defined. No `{path.to.token}` bracket syntax is used anywhere in either file (both follow the reference examples' plain-name/backtick convention instead), so there are no dangling path references. However, contrast coverage is narrow.
### Findings
- **high** No contrast target is stated for text/icons placed directly on the `accent-violet`→`accent-pink` gradient. EXPERIENCE.md's Accessibility Floor (line 80) scopes its 4.5:1 WCAG AA rule only to `text-primary`/`text-secondary` against `surface-glass` backgrounds — but the mockup (`mockups/main-screen.html`, `header` and `.fab` rules) shows the header title and FAB "+" glyph sitting straight on the gradient, and `accent-pink` (`#ff5f8f`) is light enough to plausibly fail against near-white text. *Fix:* add an explicit contrast rule (or a fixed white/near-black glyph override) for content on gradient surfaces in DESIGN.md.Colors or Accessibility Floor.
- **low** `danger` (`#ff5f5f`) has no stated contrast target against `bg-base`/`surface-glass`, and no component (e.g. the swipe-to-delete confirm sheet) documents where/how it renders. *Fix:* add a one-line contrast note and tie it to the delete-confirm component once that's specified (see §3).

## 3. Component coverage — thin
Cross-checked every component name against DESIGN.md.Components and EXPERIENCE.md.Component Patterns. Hero Card, Compact Row, FAB, Chip Button, Dialog, and Settings Row all have matching rows with real behavioral/visual rules in both files.
### Findings
- **critical** The **Ad Banner** has no row in either DESIGN.md.Components or EXPERIENCE.md.Component Patterns, despite appearing in the mockup (`.ad-banner` — distinct styling: `bg-elev` fill, top hairline, disabled-text color, centered), in State Patterns ("באנר פרסומת" row), in Key Flow 3, and in Do's/Don'ts. This is the single component that carries the product's core differentiation thesis (ad-cleanliness) — leaving it unspecified means a downstream builder has no rounding/sizing/typography/dismiss-on-purchase spec to build against. *Fix:* add an Ad Banner row to both DESIGN.md.Components (visual: fill, border, height, typography) and EXPERIENCE.md.Component Patterns (behavioral: always-visible-until-purchase, never inside add/edit flow, dismiss timing after FR-9 purchase).

## 4. State coverage — adequate
Walked all four IA surfaces (Main screen, Add/Edit dialog, Holidays dialog, Settings) against the State Patterns table. Main screen and Settings are well covered (empty, past-only, today, cold-load, offline, permission-denied, purchase in-progress/failed). Two PRD-mandated states are missing.
### Findings
- **medium** FR-5's required behavior — a holiday preset with no configured date for the current/next year must be silently omitted from the holidays list, not shown or broken — has no corresponding row in State Patterns (or in the Chip Button/Holidays-dialog Component Pattern). *Fix:* add a state row: surface = דיאלוג חגים, state = "חג ללא תאריך מוגדר לשנה הנוכחית", treatment = "לא מוצג ברשימה".
- **medium** FR-1's required validation-error behavior for the Add/Edit event dialog (empty required fields → browser validation error on save attempt) has no row in State Patterns. *Fix:* add a state row for the Add/Edit dialog covering the validation-error case.
- **low** A purchase-success state ("הפרסומות הוסרו") only appears as a Voice & Tone microcopy example (line 38), not as a formal State Patterns row alongside its in-progress/failed siblings. *Fix:* add a matching "רכישה הצליחה" row to State Patterns for consistency.

## 5. Visual reference coverage — thin
The one mockup that exists (`mockups/main-screen.html`) is correctly linked inline right after the IA table (EXPERIENCE.md line 27) with a "spine wins on conflict" note, matching the reference example's pattern.
### Findings
- **medium** Only 1 of 4 IA surfaces has any visual reference, and it depicts only the "has events" state (per the mockup's own caption) — the Add/Edit dialog, Holidays dialog, and the new/`[ASSUMPTION]` Settings screen have zero mockups. The surfaces most likely to need a visual anchor (Settings is brand-new, not inherited from the existing skeleton) are exactly the ones with none. *Fix:* at minimum, add a low-fidelity mockup or reference note for the Settings screen given its ASSUMPTION status and the page-vs-dialog ambiguity noted in §7.

## 6. Bloat & overspecification — strong
Both files are proportionate to the reference examples in length and density; prose sections stay tied to concrete product decisions (most paragraphs cite a PRD FR or research dimension directly) rather than padding with generic design-speak. No findings.

## 7. Inheritance discipline — thin
Sources frontmatter in both files resolves to real files (`prd.md`, `research.md` — both read and confirmed to exist). UJ names, FR numbers, and persona names match the PRD verbatim throughout. `surface-glass`, `text-primary`, `text-secondary` referenced in EXPERIENCE.md's Accessibility Floor resolve to real DESIGN.md color tokens.
### Findings
- **high** The Settings surface is named inconsistently and typed inconsistently across sections. EXPERIENCE.md's IA table (line 23) calls it **`[ASSUMPTION]` מסך הגדרות** ("screen"), reached via a header gear icon — implying a distinct full-screen surface. But the Dialog row in Component Patterns (line 51, "שימוש: הוספה/עריכה, חגים, **הגדרות**") lists Settings as one of the surfaces the bottom-sheet Dialog component renders on, and both purchase-state rows in State Patterns (lines 64–65) name the surface **"דיאלוג הגדרות"** ("Settings dialog"). Three of four references call it a dialog; only the IA table calls it a screen. A downstream architect cannot tell whether Settings is a routed page or a modal — this is a load-bearing routing/component decision left unresolved. *Fix:* pick one (screen or bottom-sheet dialog) and make the IA table, Component Patterns, and State Patterns all agree.

## 8. Shape fit — adequate
DESIGN.md's section order matches the canonical spec exactly: Brand & Style, Colors, Typography, Layout & Spacing, Elevation & Depth, Shapes, Components, Do's and Don'ts. EXPERIENCE.md's section order matches the reference example exactly: Foundation, IA, Voice and Tone, Component Patterns, State Patterns, Interaction Primitives, Accessibility Floor, Inspiration & Anti-patterns, Key Flows — including the extra Inspiration & Anti-patterns section, justified here by the research's competitor red-team findings and rejected-pattern list (streaks, AI copilot).
### Findings
- **medium** DESIGN.md's frontmatter deviates from `design-md-spec.md` in three places: (1) `components` values are one-line prose descriptions rather than token-maps (`design-md-spec.md` line 19 expects "component-name → object of component tokens mapped to values or `{path.to.token}` references"); (2) every `typography` role uses a free-text `note` field, but the spec reserves `note` specifically for platform-inherited values (line 48), not literal custom pixel/weight specs that this app actually owns; (3) `surface-glass` and `surface-glass-border` use `rgba()` rather than the spec's hex-string convention (line 15) — likely a legitimate need for alpha transparency, but undocumented as a deliberate deviation. *Fix:* either restructure frontmatter to match spec shape, or add a one-line note in DESIGN.md acknowledging the deliberate deviation (transparency need for glassmorphism, literal-value note usage).

## Reconciliation against PRD/research.md
- **Non-Goals honored:** no native widget, no iOS, no accounts/cloud sync, no English UI, no recurring Hebrew-date auto-reminders (Flow 2 step 5 explicitly cites this Non-Goal), no social features, and no subscription model are all correctly absent from both spines — no silent scope creep found. The dark-mode-only decision is correctly carried forward as an explicit `[ASSUMPTION]` requiring validation with שי, matching the PRD §7 open item rather than silently asserting it as final.
- **Competitive thesis (ad-cleanliness) honored well:** Brand & Style explicitly frames the differentiation against "הלוח העברי" as the incumbent — directly reflecting the research's cross-dimensional insight #2 (that הלוח העברי users also complain about ad overload), not the weaker/superseded "empty market" framing the red-team overturned. Interaction Primitives' "אסור" list and Key Flow 3 both tie directly back to PRD FR-8/9 and research dimension 3. No contradiction found here — this is the strongest-reconciled part of the pair.
- **Contradiction found — FR-6 notification-permission trigger:** PRD FR-6 requires the permission prompt to appear automatically **after the user adds their first event** (explicitly "not at onboarding"). EXPERIENCE.md never describes this trigger. The only notification-permission mechanism described anywhere in EXPERIENCE.md is the Settings Row component pattern ("מתג התראות פותח בקשת-הרשאה בפעם הראשונה בלבד" — the settings toggle opens the permission request the first time it's flipped), which is a **user-initiated, Settings-driven trigger**, not the PRD's automatic post-first-event trigger. Severity: **high** — a story-dev building only from EXPERIENCE.md would implement the wrong trigger mechanism and miss FR-6's acceptance criterion entirely. *Fix:* add the FR-6 trigger explicitly to a flow (most naturally Flow 1 or Flow 3, right after the first event is added) and to State Patterns.

## Mechanical notes
- Frontmatter `sources:` in both files point to real, existing paths (verified by reading `prd.md` and `research.md` directly at those paths).
- Name/type inconsistency: "מסך הגדרות" (IA table) vs. "דיאלוג הגדרות" (State Patterns ×2, Dialog Component Pattern) — see §7.
- No broken cross-references found: `mockups/main-screen.html` exists and matches the path cited in EXPERIENCE.md.
- Component naming is otherwise identical, character-for-character, across DESIGN.md and EXPERIENCE.md (Hero Card, Compact Row, FAB, Chip Button, Dialog, Settings Row) — the Ad Banner is the one component name that's used repeatedly (mockup, State Patterns, Key Flow 3, Do's/Don'ts) but never given a formal component row in either file (see §3).
- DESIGN.md frontmatter token shape deviates from `design-md-spec.md` in three minor ways (component tokens as prose, typography via free-text `note`, two rgba color values) — see §8; none are blocking on their own, but compound with the FAB/header contrast gap in §2.
